# Host features the browser channel could use

Research for [#3](https://github.com/jatassi/skills/issues/3), part of the visual-grilling map ([#1](https://github.com/jatassi/skills/issues/1)). Vocabulary (channel, round page, illustration, anchored comment, round submission) is from `CONTEXT.md`.

**Question.** What do agent hosts already offer that a browser channel could lean on instead of (or on top of) an agent-agnostic baseline? For each host: can it render a round page, can it return a round submission to the agent, and how would the skill detect the feature and fall back?

Researched 2026-09-26 against Claude Code v2.1.281–2.1.283 docs and changelog, the MCP Apps spec (2026-01-26), and the docs or source of VS Code, Cursor, Codex and Gemini CLI. Claims marked **(observed)** come from the tool surface of a live Claude Code desktop session (app 2.9939.2, CLI 2.1.281), not from published docs.

## Summary

| Host / feature | Renders a round page? | Returns a round submission to the agent? | Detect by | Verdict |
|---|---|---|---|---|
| Any host with a shell (the baseline) | Yes: local HTTP server + the user's browser | Yes, if the agent can block on or be woken by the server (see #2) | always present | the floor every other row falls back to |
| Claude Code desktop: Browser pane | Yes: localhost pages and project HTML files, next to the chat | **Pull only.** The agent can read the page's DOM or run JS in it, but the page cannot wake the agent | the pane's tools in the agent's tool list | best display surface on desktop; pair it with the baseline's wake-up |
| Claude Code desktop: inline widget (`visualize`) | Yes, inline in the transcript, sandboxed | **Push**: `sendPrompt(text)` posts a user message **(observed)** | `show_widget` tool present | promising for small rounds; needs a prototype |
| Claude Code desktop/CLI: Artifacts | Yes, on claude.ai, strict CSP, no localhost | Partly. The `db` capability stores the submission, but the agent must be told to read it. "Send to Claude" comments push, on Team/Enterprise only | `Artifact` tool present | poor fit for per-round traffic; conflicts with session-end cleanup |
| Claude Code CLI: `Monitor` / background tasks / long MCP calls | No | Yes: wakes the agent when a line, a result or a WebSocket message arrives | tool present / always on | the wake-up half of the baseline on Claude Code |
| Claude Code CLI: Chrome integration | Yes, in the user's Chrome | Pull only, like the Browser pane | `claude-in-chrome` tools present | opt-in (`--chrome`); fallback display for the CLI |
| Claude Code "channels" (MCP push) | No | Yes: an MCP server pushes events into the session | n/a | **not usable**: research preview, allowlisted plugins only |
| MCP elicitation (form / URL mode) | Form: plain fields only. URL: opens a page in the browser | Yes: the answer returns to the MCP server, which returns it to the agent | the host's client capabilities, seen by the server | URL mode is a clean, standard handoff; support varies by host |
| MCP Apps (`ui://`) in VS Code, Cursor, Claude web/desktop chat, Goose, ChatGPT | Yes, inline, sandboxed iframe | Yes: `ui/message`, `tools/call`, `ui/update-model-context` | the host declares `io.modelcontextprotocol/ui` in `initialize` | the richest standard path, but **not in Claude Code** today |
| VS Code integrated browser, Cursor browser | Yes | Pull only (the agent reads the page) | the host's tools | like the Browser pane |
| Codex CLI, Gemini CLI, other terminal agents | No | Only through the baseline | – | baseline only |

**Recommendation for the architecture decision (#7).** Build the baseline (local server + browser + a blocking or waking wait) as the only path the skill *needs*. Add host features as optional layers that change **where the page shows** or **how the agent is woken**, never the page or the payload:

1. **Display layer.** On Claude Code desktop, open the round page in the Browser pane instead of the system browser. Elsewhere, open the system browser, or print the link.
2. **Return layer.** Prefer a push the host already has: a long-running MCP tool call that returns when the round is submitted (backgrounded after 2 minutes, with the result delivered as a task notification in Claude Code), or `Monitor` on the server's output. Fall back to the user saying "submitted" in the terminal, then a single read.
3. **MCP Apps** are the one feature that could replace both layers at once: the round page renders inline and posts the submission with `ui/message`. They work in VS Code, Cursor and the Claude chat apps, not in Claude Code, which is the repo's primary target. If the architecture ships an MCP server anyway, attach a `ui://` resource to its round tool at low cost and let capable hosts use it, with the local-server page as the text fallback the spec requires.

Artifacts and Claude Code "channels" are not worth building on. The inline `visualize` widget is worth one prototype spike.

## Claude Code desktop

### Browser pane

- **What it is.** A tabbed browser beside the chat (Cmd/Ctrl+Shift+B). Claude "can start a dev server and open it in the Browser pane", and the pane "can also open static HTML files, PDFs, images, and videos from your project" ([desktop: Preview your app](https://code.claude.com/docs/en/desktop#preview-your-app)). Server configs live in `.claude/launch.json`; a config with `url` and no command "attaches to an already-running server" ([desktop: Configure preview servers](https://code.claude.com/docs/en/desktop#configure-preview-servers)).
- **What the agent can do there.** "it takes screenshots, inspects the DOM, clicks elements, fills forms" ([Preview your app](https://code.claude.com/docs/en/desktop#preview-your-app)). **(observed)** The tools are `preview_start` (by `launch.json` name, or `url` to open any URL without a dev server), `navigate`, `read_page`, `get_page_text`, `find`, `javascript_tool` ("for DEBUGGING and INSPECTION only"), `computer`, `resize_window`, tabs tools, and `read_console_messages` / `read_network_requests`.
- **Local pages need no approval.** "Your local dev servers and project files don't need approval" ([desktop: Browse external sites](https://code.claude.com/docs/en/desktop#browse-external-sites)). External-navigation admin controls leave localhost working: "localhost dev servers and file previews keep working" ([Restrict external browsing](https://code.claude.com/docs/en/desktop#restrict-external-browsing-for-your-organization)).
- **Round page?** Yes. A localhost round page served by the skill's server renders in the pane, and the user answers in it ("Interact with your running app directly in the Browser pane").
- **Round submission?** Pull only. Nothing in the docs or tools lets a page in the pane message the agent. The agent can pull state with `get_page_text` or `javascript_tool`, but only once it is already running a turn. So the pane is a display surface; the wake-up must come from elsewhere (the baseline server plus `Monitor`, a long MCP call, or the user typing in chat).
- **Caveats.** A user can turn the Browser off in Settings → Claude Code ([Preview your app](https://code.claude.com/docs/en/desktop#preview-your-app)). "Auto-verify" is per project (`"autoVerify": false` in `launch.json`) and is irrelevant here. Writing a `launch.json` entry into the user's project is a side effect; `preview_start` with a `url` avoids it **(observed)**.
- **Detect / fall back.** The agent checks its own tool list for the preview/Browser tools. If they are absent, it opens the system browser or prints the link. **(observed, undocumented)** `CLAUDE_CODE_ENTRYPOINT=claude-desktop` is set in tool subprocesses; a skill script could read it, but the variable is not documented, so tool presence is the safer signal.

### Inline widgets (`visualize` / "custom visuals")

- **What it is.** Claude's "custom visuals": HTML/SVG rendered inline in the conversation. In the chat apps, "clicking inside a visual sends a follow-up prompt to Claude", and visuals "are ephemeral by default" ([Help Center: Custom visuals in chat and Cowork](https://support.claude.com/en/articles/13979539-custom-visuals-in-chat-and-cowork)). They are delivered by the claude.ai `visualize` connector, which is an MCP App backed by `claudemcpcontent.com` ([anthropics/claude-code#53030](https://github.com/anthropics/claude-code/issues/53030)).
- **In Claude Code desktop (observed).** The session exposes `show_widget`. Its description says "A global sendPrompt(text) function is available — it sends a message to chat as if the user typed it", and a `read_me` call must come first. The session also has `read_widget_context`: "Widgets are rendered alongside chat from prior tool calls and can be interacted with by the user. Call this when you need to know the current state of a widget." None of this is on code.claude.com.
- **Round page?** Probably, for small rounds: the widget takes arbitrary HTML + scripts, with transparent background and host CSS variables. Size limits, the CSP, and persistence across scrollback are undocumented.
- **Round submission?** Yes, and it is the only desktop surface that pushes: `sendPrompt(text)` lands as a user message and starts a turn. The whole round submission, anchored comments included, would travel as one text message.
- **Caveats.** It depends on the user having the claude.ai `visualize` connector (not a skill dependency the repo can install). It is beta and unversioned. Widgets are ephemeral, so "past rounds viewable" would still need the baseline's saved files. It is not available in the CLI.
- **Detect / fall back.** `show_widget` present in the tool list, otherwise the Browser pane or the baseline.

### Artifacts

- **What they are.** A page Claude Code "publishes from your session to a private URL on claude.ai", available in the CLI and desktop on Pro/Max/Team/Enterprise with `/login`. They are off in the Agent SDK, on Bedrock/Vertex/Foundry, and under ZDR/HIPAA/CMEK ([artifacts: Availability](https://code.claude.com/docs/en/artifacts#availability)).
- **Round page?** Yes, with limits: one self-contained page, scripts only from five CDNs, and `fetch` only to the page's own origin ([artifacts: Page constraints](https://code.claude.com/docs/en/artifacts#page-constraints)). So it **cannot talk to a localhost server**.
- **Round submission?** No direct push:
  - The documented pattern is manual: "Add a 'Copy as prompt' button … to paste back here" ([Bring the result back to your session](https://code.claude.com/docs/en/artifacts#bring-the-result-back-to-your-session)).
  - Runtime capabilities (from the bundled `artifact-capabilities` skill, contract 0.2.60): `db` (a JSON store Claude reads with the `ArtifactData` tool), `artifact` (the page republishes itself), `comments`, `room`, `sample`, and others. `comments` with `openComposer({element})` opens the host's comment composer anchored to an element, which is almost exactly an anchored comment.
  - A comment sent with **Send to Claude** "reaches your session right away". But only artifacts "you share within your organization" take comments, which needs Team/Enterprise and v2.1.221+ ([Collect comments](https://code.claude.com/docs/en/artifacts#collect-comments-on-an-artifact)).
  - A page that saves itself does **not** wake a local session: "a new version published elsewhere no longer starts a turn; Claude learns of it from a later Artifact tool result" ([changelog 2.1.274](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)).
  - Nothing documents a wake-up on `db` writes, so the agent would have to be told to read.
- **Conflicts with the map.** Pages are uploaded to Anthropic's servers and kept until deleted or expired by retention policy ([Manage artifacts](https://code.claude.com/docs/en/artifacts#manage-artifacts-for-your-organization)). That clashes with "every file is cleaned up when the session ends": deleting an artifact is irreversible and the tool asks the user to confirm each delete. Publishing a new artifact can also prompt for permission outside auto mode.
- **Verdict.** It could serve as a *shareable export* of a finished grilling session. It is not the round-by-round channel.

## Claude Code CLI (and desktop, which runs the same engine)

- **No rendering surface** beyond the terminal. Rendering means opening the system browser, as the docs' own skill example does: the script "opens it in your browser" ([skills: codebase-visualizer example](https://code.claude.com/docs/en/skills)).
- **Wake-up mechanisms that exist today:**
  - **`Monitor`** "runs a command in the background and feeds each output line back to Claude". Watches have a deadline "5 minutes by default, at most 30 minutes", after which Claude gets one notice to re-arm. A WebSocket source exists, but Claude Code "denies URLs that point at a private, link-local, or cloud-metadata address", so a localhost WebSocket is likely refused. Use a command such as a long-poll `curl` or a tailed file instead. `Monitor` is unavailable on Bedrock/Vertex/Foundry and with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` ([tools-reference: Monitor](https://code.claude.com/docs/en/tools-reference#monitor-tool)).
  - **Background Bash**: a command past its timeout "moves … to the background instead of stopping it", and Claude is notified when it exits ([tools-reference: Background commands](https://code.claude.com/docs/en/tools-reference#background-commands)).
  - **Long MCP tool calls**: a main-conversation call "still running after two minutes moves to a background task … the result arrives as a task notification". The idle timeout is 30 min for stdio servers unless progress notifications arrive, and a per-server `timeout` overrides the wall-clock limit ([mcp: Automatic backgrounding](https://code.claude.com/docs/en/mcp#automatic-backgrounding-of-long-tool-calls)). This makes an `await_round` MCP tool a clean fit on Claude Code (details belong to #2).
- **MCP elicitation.** Form mode "shows a dialog with form fields". URL mode "asks whether to open a link in your browser". On protocol 2026-07-28 connections Claude Code declares `elicitation: {form: {}, url: {}}` ([mcp: Respond to MCP elicitation requests](https://code.claude.com/docs/en/mcp#respond-to-mcp-elicitation-requests); URL mode added in 2.1.281 per the changelog). URL mode is a standard way to open the round page and hold the tool call open until the server marks the elicitation complete. It adds a consent click per round. Form mode can't show illustrations.
- **Chrome integration** (`claude --chrome`, also VS Code) lets Claude open tabs in the user's Chrome and read DOM and console ([chrome](https://code.claude.com/docs/en/chrome)). It needs the extension, a claude.ai plan and `/login`. Like the Browser pane, it is display plus pull.
- **"Channels" (the Claude Code feature, not our glossary term).** An MCP server "pushes events into your running Claude Code session", but it is a research preview, needs `--channels`, and "only accepts plugins from an Anthropic-maintained allowlist". Custom ones need `--dangerously-load-development-channels` ([channels](https://code.claude.com/docs/en/channels#research-preview), [channels-reference](https://code.claude.com/docs/en/channels-reference)). Not shippable. **Naming hazard:** our glossary's "channel" collides with this feature name; the spec should say "browser channel" in full and never "Claude Code channel".
- **MCP Apps: not rendered.** Claude Code skips `ui://` resources in resource lists because they are "pages for a host application to render rather than content for Claude to read" ([mcp: Use MCP resources](https://code.claude.com/docs/en/mcp#use-mcp-resources)). An open feature request reports that `capabilities.extensions` "does not advertise `io.modelcontextprotocol/ui`" and a bound UI is dropped ([anthropics/claude-code#95149](https://github.com/anthropics/claude-code/issues/95149), opened 2026-09-17). The official client matrix does not list Claude Code ([MCP extension support matrix](https://modelcontextprotocol.io/extensions/client-matrix)). Unverified: whether the desktop app renders a *local* server's MCP App the way it renders the claude.ai `visualize` connector.
- **Detecting the host from a script.** `CLAUDECODE=1` is documented as set in Bash, hook and stdio MCP subprocesses ([env-vars](https://code.claude.com/docs/en/env-vars)). `CLAUDE_CODE_REMOTE=true` marks cloud sessions, where there is no local browser at all.

## Other hosts

- **MCP Apps, the standard.** Extension id `io.modelcontextprotocol/ui`, stable 2026-01-26. The host renders `text/html;profile=mcp-app` in a sandboxed iframe (default CSP `connect-src 'none'`). The view can send `ui/message` ("Host SHOULD add the message to the conversation context"), `ui/update-model-context`, and `tools/call` to its own server. "Servers SHOULD provide text-only fallback behavior for all UI-enabled tools" ([ext-apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx); [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview)).
  - **Hosts that support it:** Claude web, Claude Desktop (chat), VS Code GitHub Copilot, Microsoft 365 Copilot, Goose, Postman, MCPJam, ChatGPT, Cursor, Archestra, PostHog Code ([client matrix](https://modelcontextprotocol.io/extensions/client-matrix)).
  - **Detection** is the capability handshake, done by the MCP server, not the skill: if the client's `initialize` carries the extension, attach the UI; otherwise return text and the local link.
  - **Fit:** an MCP App is a round page, and `ui/message` delivers the round submission. The sandbox blocks `connect-src`, so the view talks to the server only via `tools/call` through the host. That is enough to post a submission.
- **VS Code (Copilot agent).** Renders MCP Apps in chat ([VS Code blog, 2026-01-26](https://code.visualstudio.com/blogs/2026/01/26/mcp-apps-support); [MCP servers in VS Code](https://code.visualstudio.com/docs/copilot/customization/mcp-servers)). An integrated browser gives agents `openBrowserPage`, `readPage`, `screenshotPage`, `clickElement`, `typeInPage`, `runPlaywrightCode`, behind the experimental `workbench.browser.enableChatTools` setting. Its pages "run in private, in-memory sessions" that the user can "explicitly share … with the agent" ([VS Code 1.110 release notes](https://code.visualstudio.com/updates/v1_110)). Display plus pull, like the Claude Code pane.
- **Cursor.** "Cursor supports the MCP Apps extension", and its capabilities table marks elicitation "Supported" ([Cursor MCP docs](https://cursor.com/docs/mcp)). A browser pane gives the Agent "full control through MCP tools", including console and network reads ([Cursor browser tool](https://cursor.com/docs/agent/tools/browser)). CLI support for either is undocumented.
- **OpenAI Codex.** The CLI, IDE extension and ChatGPT desktop app share MCP config ([Codex MCP docs](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)). The docs don't mention UI rendering, but the source shows a GUI client can declare `io.modelcontextprotocol/ui` through the app-server `initialize`, and Codex forwards it to MCP servers. The test fixture uses the VS Code extension as the client ([codex-rs/app-server-protocol common.rs](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/common.rs), [codex-rs/codex-mcp rmcp_client.rs](https://github.com/openai/codex/blob/main/codex-rs/codex-mcp/src/rmcp_client.rs)). There is also an `in_app_browser` feature flag. Treat the terminal CLI as baseline-only; the server's capability check picks up the GUI surfaces automatically.
- **Gemini CLI.** Terminal only. MCP tools can return `text`, `image`, `audio`, `resource`, `resource_link`. The docs mention no MCP Apps and no elicitation ([Gemini CLI MCP servers](https://geminicli.com/docs/tools/mcp-server/)); elicitation plumbing exists in source but is not documented. Baseline only.

## How the skill should detect and fall back

1. **Skill-side (the agent reads its own tool list).** The skill text names tools by role, not by exact id: "a browser/preview pane tool", "an inline widget tool with `sendPrompt`". It tells the agent to use them when present and otherwise open the round page URL in the system browser, or print the link if it can't. This is the only portable detection, since agents already know their tools. Environment variables (`CLAUDECODE`, the undocumented `CLAUDE_CODE_ENTRYPOINT`) can refine a helper script's behavior, but should never gate correctness.
2. **Server-side (if the architecture ships an MCP server).** Read the client's `initialize` capabilities: MCP Apps extension present → attach `ui://`; elicitation `url` present → optionally use URL mode to open the page; neither → return the link and block (or stream progress) until submission.
3. **Wake-up fallback chain on Claude Code:** long MCP call (auto-backgrounded) or `Monitor` → background Bash → the user types "done". On other hosts: a blocking call within the host's tool timeout → the user types "done".
4. **Invariant.** Every path yields the same round submission payload and saves the same files. Host features change only where the page appears and what wakes the agent.

## Open questions for the prototypes and the architecture ticket

- Does Claude Code desktop render a **local** (stdio/`.mcp.json`) server's MCP App, or only claude.ai connectors like `visualize`? One test server logging its `initialize` params answers it.
- `visualize` widget limits: max HTML size, CSP, whether `sendPrompt` works in Claude Code desktop exactly as in chat, and whether widgets survive session resume.
- Does a Browser-pane page run the same as in a normal browser: `fetch` to its own localhost origin, `localStorage`, `postMessage`? Expected yes (it's a Chromium tab), untested.
- Is a localhost `ws://` truly refused by `Monitor`'s WebSocket source? The docs' "private" list likely includes loopback.
